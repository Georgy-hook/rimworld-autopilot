## Contract and validation

`GET /api/v1/sustenance/context` provides real alternatives and facts. `POST /api/v1/sustenance/policy` accepts only a freshly regenerated exact option key, never arbitrary recipe/code/property names. Python partitions keys into five registered actions and rereads options before posting. Native Laya chooses purpose, target subject and actual policy/operator; short aliases plus five separate consequence fields retain subject hunger/medicine, kitchen cleanliness and storage temperature evidence. Defer is available at every stage. No deterministic chosen policy. Applied means policy/bill/job acceptance only. Fresh missing options return applied=false.

Python tests cover domain partition/cooldown, stale-target rejection, native downside/defer choices, exact-key posting and distinguishing pasture shortfalls from sufficient stored feed. An 80-animal regression verifies the final starving subject remains visible/selectable within 312 state tokens, with every consequence field retained. Shared C# build verifies installed API signatures. No game/model launches were performed.

Remaining explicit boundaries: kitchen relocation, fertilized-egg breeding planner, pen construction/route topology optimizer, bill ingredient reservation planner and targeted sex-filter split of pens require architect/planning integration. Odyssey defs are absent locally; conditional fishing is implemented using native zone/jobgiver gates, not locally exercised.

Custom diet choices copy the pawn's actual current policy into a dedicated per-pawn policy and allow/avoid one loaded reachable edible definition. Exclusion requires another currently allowed reachable food. Existing special ingredient filters are preserved; no policy edits affect other pawns. Raw/human/insect foods retain native ideology, mood and poisoning consequences.

Preflight closure: kitchen cleanup checks explicit reach and loaded capacity; ingredients respect pawn-specific forbidden status, bill search radius and Thing-level filters/quality; table workers respect loaded capacity and table forbidding/reservation. Observation uses parameterless native bill subtype previews without persistent bill IDs; IDs initialize only for accepted additions. Existing completed compatible bills are reused. Milk/wool use pure native HasJobOnThing observations; fishing creates a job only at execution and refuses a job targeting a different zone.

Fishing bootstrap (shared assembly only): researched active Odyssey permits an ordinary native fishing zone on visible zoneable passable fish-bearing water with a reachable dry bank. Exact footprint is revalidated; one shoreline candidate per actual water type, one catch cycle then stop. Existing-zone context includes population fraction/floor, frozen state, owned fish, mode/repeat/target and allowed state. JobDriver_Fish explicitly uses target A for fishing water and B for standing bank; execution checks the selected zone against A. Native ideology/jobgiver/catch mechanics decide completion. Local Odyssey Data is absent, so runtime fishing validation remains unavailable.
Existing allowed unfrozen fishing zones can be set/rearmed to one native catch cycle while retaining their population floor; this closes repeated finite fishing after the first bootstrap batch.
